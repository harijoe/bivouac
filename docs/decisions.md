# Decisions

- **Hono + better-sqlite3 + dockerode**: small, fast, synchronous DB fits a single-node daemon. SSE via Hono streaming.
- **Daemon drives the agent via `docker exec`** into a long-lived task container (supervisor as PID 1 runs the dev server). Keeps git creds/tokens inside the task container only; no docker socket in task containers.
- **Fake claude ships in the task image** (`/opt/bivouac/fake-claude`), selected by `BIVOUAC_CLAUDE_BIN`, so CI and VM e2e exercise the same image without tokens.
- **Task ids are integers** (`t-42`); preview host is `t-<id>.<project>.<domain>`; default domain `<tailscale-ip-dashed>.sslip.io`.
- **Git runs on the host (daemon), not in the task container.** The daemon clones/pushes with the project token injected as an HTTP header; the token never enters a task container or `.git/config`. The agent commits locally; the user pushes via the dashboard.
- **Traefik joins each task's private network** (instead of tasks joining a shared one), so tasks can't reach each other's dev servers; the preview is routed per task.
- **Instruction injection uses a queue + `--resume`** (not `--input-format stream-json`): simple and deterministic; instructions land at the next iteration boundary.
- **Token budget counts input + output + cache-creation tokens** (cache reads excluded). Cost budget is also enforced by the CLI itself via `--max-budget-usd <remaining>`.

## v0.2

- **web / executor split.** One image, two services. `web` (public, non-root, no Docker socket) serves the dashboard, API, MCP and OAuth. `executor` (root, Docker socket) is reachable only from `web` on an internal Docker network, with a shared secret, and accepts only: prepare repo, start/stop/destroy/exec in *task containers it names itself*, read/write a few workspace files, push, and `claude setup-token` sessions. It never takes images, mounts, networks or labels from its caller.
- **Routes come from the database, not Docker labels.** Traefik uses the HTTP provider (`web:3001/internal/traefik`, polled every second). A rename is a DB update, live within ~1 s with no container restart. The internal listener (3001) is never routed by Traefik.
- **Preview access = forwardAuth to `web`.** Entry by one-time ticket (owner) or share token in the URL swaps for a host-bound, HMAC-signed cookie; the 302 drops the secret from the URL. forwardAuth returns the remaining `Cookie` header and Traefik's `authResponseHeaders: Cookie` replaces the request header, so the app never sees `bv_preview`. Share cookies are re-checked against the DB (revocation is immediate).
- **Identity = the instance's own GitHub App** (manifest flow). Login uses its user authorization; git uses installation tokens narrowed to one repo and to `read`/`write` permission sets, cached until 5 min before expiry. Allow-list stores numeric ids; orgs/teams are checked live with the installation token.
- **MCP is stateless** (new server + transport per request, JSON responses): nothing to lose between requests or on restart. OAuth server written in-house (small, fully tested): DCR, S256-only PKCE, rotating refresh tokens with reuse detection, hashed storage.
- **Setup link = hashed code + signed cookie.** Valid until the GitHub step creates the admin, then closed. `bivouac reset-admin` creates a new one; changing the domain does the same because the GitHub App must be recreated.
- **Task name is the preview label**; the branch stays `agent/t-<id>-<name>` so a rename or name reuse never touches git history.
- **Certificates per host via HTTP-01**, on demand (no DNS API needed). The sslip.io/own-domain wildcard is *not* a wildcard certificate.
- **UI is English only for now**; strings are plain JSX, easy to extract later.

## v0.3

- **One deployment script for install and update.** `apply.sh` (shipped in the daemon image) renders compose, systemd units and the firewall from `/etc/bivouac/bivouac.env`, backs up, pulls, recreates, waits for health and rolls back. `install.sh` (prerequisites, first config) and the dashboard updater both run it, so there is no second implementation to drift. It writes its progress to `update-status.json` in the web data dir, which survives the web restart and is what the dashboard polls.
- **The updater is an ephemeral container started by the executor, from the *new* image.** `web` still has no Docker socket. The executor accepts only a semver (never an image name), derives the registry from its own image, and starts `bivouac-updater` (privileged, host PID namespace) which copies the new `apply.sh` to `/opt/bivouac` and runs it in the host namespaces with `nsenter`. Rationale: the script must run on the host (systemd, firewall, compose) and the new version's logic must drive the update. The container is outside the compose project, so recreating the services does not kill it. The executor already is root-equivalent (Docker socket), so this adds no new privilege level, only a new fixed-shape operation.
- **Backups by graceful stop.** `docker stop bivouac-web` checkpoints the SQLite WAL, then the data dir (database + key), env file, compose file and unit are copied to `/var/lib/bivouac/backups/<utc>` (3 kept). Rollback restores them and brings the old images up (they are still local). No dependence on a `sqlite3` binary or on the old version knowing a backup command.
- **Releases come from the GitHub releases API** (configurable `BIVOUAC_RELEASES_URL`, same JSON format, so tests point at a fake server). Drafts, pre-releases and non-semver tags are ignored; the highest semver wins, not the most recent date.
- **Scheduling = refusing new work, not pausing old work.** While an update is scheduled or running, `create_task`, `resume_task` and instructions that would restart a task fail with an explanatory error. The scheduler tick (10 s) starts the update when no task is queued or running. "Update now" stops tasks through the normal stop path (status `stopped`, resumable).
- **No re-attachment of running agents after a restart.** Task containers survive an update, but the agent is a `docker exec` whose stdout is streamed over an HTTP request from `web` through `executor`; when either restarts, the stream (and with it the parsing of the result, usage and the success loop state) is gone, and the CLI session cannot be re-read mid-turn. Re-attaching would mean persisting stream-json to disk in the container and replaying it, plus a way to know whether the success check already ran: a large change for a rare case. A clean stop and resume (`--resume` keeps the conversation) is the supported path, and is what "update now" does.
- **Ports.** `ports` is an ordered map name → port; the first is primary and keeps `<task>.<project>.<domain>`, others are `<port>.<task>.<project>.<domain>` (one more label, never ambiguous: project and task names cannot contain dots). `dev.port` stays a single port named `web`. Share links and tickets are per task, so any port of the task accepts them (the cookie stays bound to the host).
- **Sidecars** are plain containers on the task network with the service name as DNS alias, `no-new-privileges`, `NET_RAW` dropped, CPU/memory/pids limits and an optional named volume, all labelled with the task id so destroy removes them. The executor re-validates the `services` section itself (image reference, env names, volume path) because the file is written by an agent. Images are pulled on first use.
- **Firewall.** Task networks get a predictable bridge name `bvt<id>`; one static rule set (`INPUT -i bvt+ → BIVOUAC-INPUT`, which accepts established traffic and drops the rest; `DOCKER-USER` drops `169.254.0.0/16`) covers every present and future task network, so nothing has to be added per task. It lives in `bivouac-firewall.service` (ordered after Docker, before bivouac). Cross-network isolation (web, executor) is Docker's own bridge isolation, verified by the e2e rather than duplicated.
- **bivouac.yml is re-read at each agent session** from the task working copy (not only from the pushed branch: the agent commits locally and may not push). Invalid file → keep the last valid parsed configuration, store the error, tell the agent in its next prompt.
- **Project context from a bare git mirror** in the web data dir, fetched with the repo-limited token at every call (a failed fetch serves the stale mirror with a warning). Secrets are excluded twice: by path (`.env*`, keys, credentials, git-ignored files via the root `.gitignore`) and by content (token patterns and `password=…` values masked), including in task prompts, agent messages and check output. The snapshot is a budgeted Markdown document (documents keep their head and tail, never silently dropped).

## v0.3.1

- **Tool versions with mise, not corepack.** Node 25 and later no longer ship corepack, and the owner's example needs Node 26 + pnpm 11, so `packageManager` is mapped to a mise tool (`pnpm@11.0.1`), not activated by corepack. One generated file (`/workspace/.bivouac/mise.toml`, loaded through `MISE_OVERRIDE_CONFIG_FILENAMES`, which makes mise ignore the repository's own `mise.toml`) holds the merged result, so `runtime:` really wins. Tools and versions are validated with strict patterns before being written (no TOML injection). The cache is a Docker volume per project (`<prefix>-mise-<project>`), removed by the uninstaller with the other labelled volumes (not on project removal: a known leftover). pnpm 11 and other binaries need `libatomic1`, added to the image.
- **`engines.node` is a range, mise installs prefixes.** The lowest version of the range is installed (`>=26` → `26`). It is a heuristic; `runtime:` overrides it.
- **`blocked` is a file, not a tool.** The agent writes `/workspace/.bivouac/blocked.md` (outside the repository, so it is never committed); the runner reads and clears it after each agent session. A file works with any CLI version and needs no MCP server inside the container.
- **`stuck`** compares the output of two consecutive failed checks and a fingerprint of the working tree (a throwaway git index, `.bivouac` excluded, so the agent's own staging area is untouched).
- **The login code is typed, then Enter is sent in a separate write** (Ink treats a single write as a paste). The screen of `claude setup-token` is rebuilt with `@xterm/headless` before extracting anything, because the CLI repaints only changed cells.
- **Costs with a subscription** are labelled "estimated API equivalent" (`costKind` in the API and in `get_task`); the dollar budget keeps bounding consumption either way.

## v0.4

- **CSP: `style-src 'self' 'unsafe-inline'`.** shadcn/Radix (popper positioning), Sonner and the virtualized log list set `style` attributes, which a strict `style-src` blocks. Scripts stay `script-src 'self'` (no inline, no eval); the theme initialiser is a served file (`/theme-init.js`), not an inline script. Style injection cannot execute code, and the app has no user-supplied HTML.

## v0.4.1

- **Attempt = the `iteration` stored on each event; markers are attached to the attempt that follows them.** Instructions, status changes (stopped, blocked, stuck, budget, max attempts, failed, succeeded, resumed) and limit changes are "markers": an event that is a marker belongs to the first attempt that *starts after it* (or, for the newest, is shown above it). That puts an instruction sent while attempt N runs before attempt N+1, where it is applied. Everything is computed by SQL (`attempts.ts`) so a page of attempts costs a few indexed queries, not a scan of the history; the events of an attempt are fetched only when it is opened.
- **No SSE replay for the task page** (`?tail=1`): the page loads its own history by pages and takes only new events from the stream; after a reconnection it reloads the first page.
- **Docker's `OOMKilled` flag is not trusted alone.** It is sometimes false when the process dies instantly (seen in the integration test), so an unrequested exit 137 of a service is reported as a probable memory kill, with a more careful sentence. Services get no swap, so the kill is immediate and attributable.
- **Plain `resume` extends the attempt limit only when it is exhausted**, and records it in the history; a limit the owner raised explicitly is kept. A budget-stopped task refuses a plain resume with the way out, because it would stop again at once.

## v0.5

- **Attempt diffs use snapshot commits, not branch ranges.** At the start and end of every attempt the executor builds a commit of the whole working tree (throwaway index, `.bivouac` and ignored files excluded) and pins it under `refs/bivouac/marks/`. Diffing two of them shows committed and uncommitted work alike, and an attempt with no commit still has a diff. The commits between the two heads are listed separately. Revisions accepted by the API are limited to 40-hex ids and `origin/<branch>`.
- **The supervisor owns preview health** (it knows its child, and keeps working while the daemon restarts). It writes `health.json`; the daemon only reads it (`PreviewWatch`, every 10 s, for all tasks, not just running ones) and turns changes into events and notes for the agent. Restart delays 1, 2, 4, 8, 15, 30, 60, 60 s, then `down` until the dev command changes or a restart is requested. A server that was healthy and stops answering for 30 s is killed and restarted.
- **Aliases are a project property pointing at a task.** The alias can never be a project name (both are one label under the domain, `x.y.<domain>` must stay unambiguous). Public paths belong to the project (administrator settings), not to `bivouac.yml`, which an agent can edit: an agent can never make a path public. Public paths apply to the alias host only.
- **Screenshots run in the task container**, with Debian's Chromium driven by `playwright-core` through CDP (full page cut at 5000 px, a scaled "small" copy for chat clients). Images are copied to the web data directory (the web service cannot read task workspaces) and bounded per task. Unit tests use a local Chromium when there is one (CI has Chrome); the Docker integration test uses the image's own.
- **Environment snapshots = an archive of git-ignored files, restored before `setup`, and `setup` always runs.** Alternatives considered: `docker commit` (misses the bind-mounted workspace where `node_modules` lives, and bakes secrets and state into an image), package-manager cache volumes (still reinstall and link every package, and each tool needs its own), skipping `setup` on a match (a stale build output or a damaged snapshot would silently give a wrong environment). Running `setup` on top costs a few seconds and makes a wrong snapshot harmless: correctness never depends on the fingerprint. Not snapshotted: service data (Postgres volumes: initialisation and migrations are quick and a database is state the agent changes), `.env`-like files, keys, logs. No lock file, no snapshot. Archives are plain tar (no compression: restore is I/O bound, 800 MB in under 3 s here) under `<data>/projects/<project>/snapshots`, 3 kept per project, none above 3 GB.
- **"Rebuild" discards snapshots; there is no idle build.** The next task's own `setup` produces the new one exactly as every task builds it, so a snapshot is a by-product that costs no extra container. The settings page says so.
